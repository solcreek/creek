## Overview

Creek provides a remote MCP server at `mcp.creek.dev` that lets any AI agent deploy websites without installing the CLI.

One tool call. Zero installation. 10 seconds to a live URL.

## Connect

Add to your MCP client config (Claude Desktop, Cursor, Windsurf, etc.):

```json
{
  "mcpServers": {
    "creek": {
      "url": "https://mcp.creek.dev",
      "headers": {
        "Authorization": "Bearer <CREEK_TOKEN>"
      }
    }
  }
}
```

No API key needed for sandbox tools. Authenticated tools (build log, resources) read `Authorization: Bearer <key>` or `x-api-key` from this HTTP request — never as a tool argument.

## Results

Every tool answers with one JSON text block:

- **Success:** `{ "ok": true, ... }` — the tool's fields sit next to `ok`.
- **Failure:** `{ "ok": false, "error": "<code>", "message": "...", ... }`, and the MCP result has `isError: true`. An API error keeps the API's code (`not_found`, `insufficient_scope`, `binding_conflict`, `rate_limited`, …), its HTTP `status`, and its other fields under `details`.
- **Network failure:** `{ "ok": false, "error": "api_unreachable", "message", "retryable" }`. `retryable` is `true` only when nothing can have been changed: a read, or a request refused before it was sent. Otherwise `retryable: false` and `mayHaveApplied: true` — check the effect (for example with `list_deployments`) before calling again.

Branch on `ok` and `error`, never on the wording of `message`.

Every tool also declares MCP annotations — `readOnlyHint`, `destructiveHint`, `idempotentHint` — so a client can ask the user before a destructive call. Read-only: the `list_*`, `get_*` and status tools and `wait_for_deployment`. Destructive: `deploy_delete`, `env_set`, `env_rm`, `deploy_prod`, `rollback`, `detach_resource`, `delete_resource`, `query_database`.

## Available Tools

### `deploy`

Deploy files to a sandbox preview (60 min).

**Input:**
- `files` — `Record<string, string>` — file path to content (UTF-8 strings, not base64)
- `source` — `string` (optional) — source identifier for tracking

**Output:** `{ ok: true, url, sandboxId, deployDurationMs, expiresAt, expiresInSeconds, proof }` — `proof` is `{ ok, status, title, ttfbMs }`.

Every failure after the sandbox was created still carries its `sandboxId` — call `deploy_status` with it rather than deploying again:

- `verify_failed` — the sandbox deployed but the preview URL is not live (`url` and `proof` included).
- `deploy_failed` — the build failed (`failedStep`, `errorMessage`).
- `sandbox_expired` — it expired before going live.
- `timeout` — not live after 30 s (`sandboxStatus` is the last status seen); it may still finish.

### `deploy_demo`

Deploy a sample page instantly. Great for testing connectivity.

**Input:** none

**Output:** same as `deploy`, plus `message`.

### `deploy_status`

Check the status of a sandbox deployment.

**Input:**
- `sandboxId` — `string`

**Output:** `{ ok: true, sandboxId, status, previewUrl, expiresInSeconds, claimable, failedStep, errorMessage, … }`. An unknown id is `{ ok: false, error: "not_found", status: 404, sandboxId }`.

### `deploy_delete`

Delete a sandbox before it expires. Only the client that created it can delete it (matched by IP).

**Input:**
- `sandboxId` — `string`

**Output:** `{ ok: true, sandboxId, deleted: true }`. Errors: `forbidden` (another client created it), `already_expired`, `not_found`.

### `list_projects`

List projects in the authenticated team.

**Auth:** `Authorization: Bearer` or `x-api-key`

**Output:** `{ ok, projects: [{ id, slug, framework, productionDeploymentId, productionBranch, githubRepo, updatedAt }] }`

### `get_status`

Remote status for one project.

**Input:** `projectSlug`

**Output:** `{ ok, type: "project", slug, framework, productionDeploymentId, latestDeployment }`

### `env_ls`

List env var **keys** only (values are never returned), with each value's deploy target.

**Input:** `projectSlug`

**Output:** `{ ok, project, keys: string[], vars: { key, target }[] }`

### `env_set`

Create or update an env var. Does not restart the worker. `target` is `production`, `preview` (branch deploys) or `all` (default); a deploy uses its own target's value, else the `all` value.

**Input:** `projectSlug`, `key`, `value`, `target?`

**Output:** `{ ok, key, target, pendingDeploy: true, nextStep: "Call deploy_prod …" }` — the value is never echoed. `target_unsupported` means the server stored the value for all deploys.

### `env_rm`

Remove an env var: one target's value, or every value of the key without `target`. Same pending-deploy caveat as `env_set`.

**Input:** `projectSlug`, `key`, `target?`

### `deploy_prod`

Trigger a production deploy of the latest commit on the project's GitHub production branch (`POST /github/deploy-latest`). Does **not** wait for the build.

**Input:** `projectSlug`

**Output:** `{ ok, triggered, branch, commitSha, deploymentId, version, status, pending: true, nextStep }`. The trigger returns no id, so the tool looks for the new deployment for up to ~10 s; `deploymentId` is `null` if it did not appear in time (or the key lacks `project:read`) — then find it with `list_deployments`. Follow it with `wait_for_deployment`.

Requires a GitHub connection. Projects without one get `not_found` / "Project has no GitHub connection".

### `list_deployments`

Recent deployments, newest first.

**Input:** `projectSlug`

**Output:** `{ ok, project, deployments: [{ id, version, status, branch, triggerType, createdAt }] }` — pick an active row whose `triggerType` is not `rollback` as the `rollback` target.

### `get_deployment`

Read one deployment.

**Input:** `projectSlug`, `deploymentId` (8-char short id or full uuid)

**Output:** `{ ok, project, deploymentId, version, status, terminal, branch, commitSha, triggerType, failedStep, errorMessage, errorCode, errorHint, url, previewUrl, isProduction, createdAt, nextStep? }`. `status` is in flight (`queued`, `building`, `uploading`, `deploying`) or final (`active`, `failed`, `cancelled`); `terminal` is `true` once it is final. `url` is set once the deployment is active. On failure `nextStep` points at `get_build_log`.

### `wait_for_deployment`

Wait until a deployment is final.

**Input:** `projectSlug`, `deploymentId`, `timeoutSeconds?` (default 45, max 300 — keep it below your client's tool-call timeout)

**Output:** the `get_deployment` fields with `ok: true` when it is `active`. Otherwise an error result with the same fields: `deployment_failed` (see `failedStep`, `errorCode`, then `get_build_log`), `deployment_cancelled`, or `timeout` with `retryable: true` when it is still running — call it again.

### `rollback`

Roll production back to a previous active deployment.

**Input:** `projectSlug`, required `deploymentId` (active non-rollback row from `list_deployments`), optional `message`

### Resources

- `list_resources` (`kind?`) → `{ ok, resources: [...] }`
- `create_resource` (`kind`, `name`) → `{ ok, id, kind, name, … }`
- `attach_resource` (`projectSlug`, `resourceId`, `bindingName`) → `{ ok, project, resourceId, bindingName }`
- `detach_resource` (`projectSlug`, `bindingName`) → `{ ok, project, bindingName, detached: true }`
- `rename_resource` (`resourceId`, `name`) → `{ ok, resourceId, name, … }`
- `delete_resource` (`resourceId`) → `{ ok, resourceId, deleted: true }`
- `query_database` (`resourceId`, `sql`, `params?`) → `{ ok, columns, rows, meta }`

## Example

An AI agent can deploy a website in a single tool call:

```
User: "Create a portfolio page and deploy it"

Agent:
1. Generates HTML/CSS
2. Calls creek.deploy({ files: { "index.html": "<html>...", "style.css": "..." } })
3. Returns: "Deployed to https://a1b2c3d4.creeksandbox.com"
```

## Authentication

| Tools | Auth required |
|-------|:------------:|
| Sandbox tools (`deploy`, `deploy_demo`, `deploy_status`, `deploy_delete`) | No |
| Build log (`get_build_log`) | `Authorization: Bearer` or `x-api-key` header |
| Projects (`list_projects`, `get_status`) | same header |
| Env (`env_ls`, `env_set`, `env_rm`) | same header |
| Production (`deploy_prod`, `list_deployments`, `get_deployment`, `wait_for_deployment`, `rollback`) | same header |
| Resources (`list_resources`, `create_resource`, `attach_resource`, `detach_resource`, `delete_resource`, `rename_resource`, `query_database`) | same header |

`deploy_prod` requires a GitHub connection on the project (same as `creek deploy --from-github --prod`). It returns as soon as the build is dispatched, with the `deploymentId` to pass to `wait_for_deployment`; on failure read `get_build_log`. `env_set` / `env_rm` do not restart the worker — follow with `deploy_prod`.

Do not pass `apiKey` as a tool argument. Prefer the CLI when you have a shell (`~/.creek/config.json` or `CREEK_TOKEN`).

## Rate Limits

MCP requests are rate-limited per client IP (not per MCP server):

- **10 sandbox deploys per hour** per IP
- **Demo deploys are exempt** from rate limits
- Rate limit info is returned in tool output when triggered

## Technical Details

- **Transport:** Streamable HTTP (Web Standard)
- **Runtime:** Cloudflare Workers
- **Protocol:** MCP 2025-03-26
- **Endpoint:** `https://mcp.creek.dev` (`/mcp` still works)
- **Health check:** `https://mcp.creek.dev/health`

The MCP server is a stateless protocol translator. Sandbox tools (`deploy`, `deploy_demo`, …) call the Sandbox API; authenticated project/env/deploy tools call the Control Plane. No data is stored in the MCP server itself.
